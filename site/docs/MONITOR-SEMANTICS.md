# Monitor presentation and state semantics

Reviewed 2026-11-01 (Asia/Shanghai). Scope: the operations monitor at
`http://127.0.0.1:8765/`, generated by `tools/dashboard.py`. The research document
remains at `/index.html`.

The monitor prioritises execution, consumer expectations and service boundaries.
Its dark palette is retained. The dependency matrix and operator diagrams keep
readable text and scroll inside their own regions; consumer cards use three,
two or one columns according to available width. Navigation connects the
operations view to consumers, history and the research evidence.

| Element | What its state means | What it does not establish |
|---|---|---|
| Overall OK | No fault in the observations and named sampler verdict; fresh data required | Completion of running work or scientific acceptance |
| LIVE | A fresh response and usable monotonic sample sequence; backward/stalled sequence withdraws LIVE | Availability of unmeasured dependencies |
| Chain PASS / SKIP | Recorded execution outcome / boundary unexercised | A SKIP is never counted as a passed chain |
| RUNNING | Work in progress; shown explicitly in the summary | A completed check |
| Module colour | Worst judged state of its users; all IDLE stays IDLE | Independent qualification of that module |
| Dependency dot | The current state of its chain | A permanently green dependency inferred from topology |
| Service boundary | Only explicit OK is green; missing/unknown observations remain visible | Model competence or scientific reasoning quality |
| Consumer MATCH | Gate S outcome equals the declared expectation, with current input binding and freshness | Universal validity of the project |
| Consumer CONTROL OK | The declared negative control was actually rejected | Gate S PASS or successful scientific findings |
| Consumer STALE | Cached verdict withdrawn; freshness absent/expired or declared inputs changed | A new failed gate execution |
| Repair phases | Latest logged attempt, in a timestamped rendered snapshot; inactive repair stages are SKIP | Proof that an active fault has cleared |
| Healed count | Verified recovered events within 24 hours; explicitly failed outcomes excluded | Every terminal verification event was a successful recovery |
| Evolution ledger | Historical record with its own date and source version | Live qualification of current source, or zero current defects |
| Fault incidents | Recorded episodes in the last 24 hours, separated by more than 10 minutes | All listed faults remain active |
| Source ages | File modification ages; different sources update for different reasons | An old quiet recovery log is a service failure |

The page uses the existing `/api/status` feed. Every poll updates chain dots,
dependency cells, module headers, service headers/cells, tooltips, ages, summaries
and consumer cards together. Visible tabs request status every ten seconds and
timestamped recovery/evolution/source/history adjuncts every minute; hidden
tabs slow polling to one minute. Sequence not advancing for 45 seconds, backward
sequence, invalid responses, HTTP errors and an eight-second request timeout
cannot leave a green LIVE badge. The previous observation is retained and
explicitly labelled as cached. A deliberate sequence reset requires a page
reload to establish a new observation baseline.

The presentation guard recomputes named state and rejects a contradictory
cached overall verdict. It does not run probes, rerun experiments, or rewrite
sampler evidence. Recovery terminal events from an earlier attempt or another
service cannot verify a new attempt. Controls and input binding continue to
use the existing project registry and `consumer_freshness` rules.

Validation: targeted dashboard, consumer-binding and presentation regression
tests; executed JavaScript with DOM doubles for PASS-to-FAIL transitions,
unobservable services and unavailable transport; live Chrome checks at desktop
and 390 px widths, consumer details, dependency-cell consistency and console
errors. These checks do not replace a complete framework audit or a clean
24-hour stability run.
