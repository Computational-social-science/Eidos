A framework that audits its own claims

Eidos checks what most tooling never checks: whether the sentence a paper argues for is the sentence its evidence licenses. It then applies that check to itself, in public, with the failures left visible.

01Why it exists

A project can pass twenty artefact gates with an unsupported central sentence. Those gates answer questions about files — did the pipeline run, is the figure legible, does the citation resolve — and none of them asks whether the evidence supports the claim. The failure is invisible to tooling because it is not a defect in an artefact; it is a gap between the artefact and the sentence.

Eidos separates two things usually conflated:

  • Verification — did we build it correctly, reproducibly, and (where the claim is formal) provably?
  • Validation — is the claim we are making the claim the evidence licenses?

Verification is strong by construction here: eleven chains, negative controls, CI on two Python versions, and a Lean 4 audit that has been run against real proofs. Validation is a single gate, and it is deliberately the strictest thing in the repository.

What Gate S refuses

  1. A claim whose text is not in the deliverable.
  2. An evidence pointer that no longer resolves, or a value that moved.
  3. “Supported” without a preregistered design and a negative control.
  4. A scope axis neither declared nor excluded with a reason.
  5. A referee document whose open objections are under-reported.
  6. A formal claim the Lean chain cannot reproduce.

02Architecture

Chains, not modules, are the unit of trust. Each chain is exercised end to end — a real render, a real MLflow run, a real Lean build — and reports PASS, SKIP or FAIL. A module that imports is not a module that works; the chain audit exists because that distinction was learned the expensive way.

05The demo, and its limit

What this demonstrates — and what it does not

Does. A short-time operator fitted on data supports system-level computation: fixed points, their stability, their parameter dependence — without writing the governing equation down.

Does not. It is not a PDE solver, and no claim is made outside the training interval merely because extrapolation happened to work: the measured accuracy beyond λ = 0.6 reflects a smooth one-dimensional map, not a general result. Applying the machinery to token sequences would be a category error — those are not C¹ function spaces.

The two adopters are deliberately unlike — a Python repository with a manuscript, and a Lean library with no Python and no manuscript. If the registry only fitted the first, the generality claim would be empty.

07What the framework does not claim

Referee simulation. 8 objections recorded, 0 open. The gate parses the tags in docs/REFEREE_SIM.md and refuses a register whose count disagrees.

Known limits. Coverage is uneven — framework/inference is exercised mainly by chains, not unit tests. The Lean chain is verified on two external projects, not on a project this framework gates. Quarto is absent on the build host, so a project's PDF path cannot be exercised end to end here.

One adopter proves an interface, not a field. Two show the registry is not shaped around one repository. Nothing here shows that the gates improve a project's science; that would need a control group this programme does not have.

What is generated, what is reviewed

Every number on this page is computed at build time. The prose is reviewed by hand; the figures are not — architecture_svg, the chain table and the extrapolation panel are all produced from data or from the code that runs the chains.

The page has no external script, font or network call: it opens from disk. Formulas are MathML, not images.
